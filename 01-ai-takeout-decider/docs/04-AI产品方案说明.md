# AI 产品方案说明

> 文档目的：说明哪里需要 AI、哪里必须使用规则、如何评估和控制错误  
> 当前实现：基于模拟菜单的确定性多目标排序 [F]  
> 未来设想：自然语言理解、营养估算与个性化排序 [H]

## 1. 核心产品判断

「这顿」不是一个“让大模型自由回答今天吃什么”的聊天机器人。外卖决策包含不能违反的预算、时限和排除项，因此系统必须先保证正确，再优化个性化和解释。

采用三层结构：

1. **规则层**：负责硬约束和安全边界，结果必须可验证。
2. **排序层**：负责多目标权衡、候选多样化和个性化。
3. **生成层**：负责理解自然语言与生成有依据的简短解释，不决定是否违反硬约束。

## 2. 为什么不让大模型直接排序

| 任务 | 最合适机制 | 原因 |
|---|---|---|
| 预算、时限、排除项过滤 | 确定性规则 | 必须 0 违规，可审计、可测试 |
| 健康、味道、价格、速度权衡 | 可解释排序模型 | 需要稳定分数、权重和离线评估 |
| 三个结果的差异化 | 重排序规则 | 防止 Top 3 都是相似菜品 |
| “今天想清淡但别太寡淡”的理解 | 受约束的语言模型 | 自然语言表达丰富，适合映射为结构化偏好 |
| 推荐理由 | 模板 + 受约束生成 | 保证只引用已有属性，同时保持自然表达 |
| 营养区间 | 菜谱/商家数据 + 估算模型 | 需要数值基准与不确定性，不适合凭语言生成 |

## 3. 推荐系统流程

```mermaid
flowchart LR
    A[用户输入与当餐情境] --> B[偏好解析]
    B --> C{硬约束过滤}
    D[授权菜单/价格/ETA] --> C
    C -->|无候选| X[不放宽约束，提示调整]
    C -->|候选集| E[特征归一化]
    E --> F[多目标加权排序]
    G[历史反馈档案] --> F
    F --> H[差异化重排序]
    H --> I[主推荐 / 时间更稳 / 营养更优]
    I --> J[基于证据生成理由与取舍]
    J --> K[展示置信度与数据新鲜度]
    K --> L[选择、替换、跳转、反馈]
    L --> G
```

## 4. 输入与输出契约

### 4.1 输入结构

```json
{
  "context": {
    "location_zone": "杭州·滨江",
    "meal_period": "午餐"
  },
  "hard_constraints": {
    "budget_max": 32,
    "delivery_minutes_max": 40,
    "excluded_flags": ["辣", "花生"]
  },
  "soft_preferences": {
    "health": 25,
    "taste": 30,
    "price": 25,
    "speed": 20
  },
  "adaptive_answer": "taste",
  "profile_version": "anonymous-local-v1"
}
```

### 4.2 输出结构

每个结果必须包含：菜品与商家 ID、价格、预计送达、营养区间、四项分数、总分、推荐位置、理由、主要取舍、置信度、数据时间戳和可用下单平台。

```json
{
  "position": "primary",
  "item_id": "grain-chicken-bowl",
  "score": 86,
  "factor_scores": {
    "health": 91,
    "taste": 82,

    "speed": 58
  },
  "reason": "高蛋白，营养负担更轻",
  "tradeoff": "价格接近本餐预算上限",
  "nutrition_range_kcal": [430, 520],
  "confidence": "high",
  "data_freshness_seconds": 120
}
```

## 5. 排序逻辑

### 5.1 硬过滤

候选菜品仅在同时满足以下条件时进入排序：

- `price ≤ budget_max`
- `delivery_minutes ≤ delivery_minutes_max`
- `item_flags ∩ excluded_flags = ∅`

如果候选数为 0，系统不得静默放宽条件。用户必须明确修改预算、时间或排除项。

### 5.2 权重归一化

四项软偏好先转为总和 100 的权重。场景模式提供默认权重，动态问题只为一个因子增加权重，再重新归一化。

### 5.3 多目标得分

```text
总分 = 健康分×健康权重
     + 味道分×味道权重
     + 价格适配分×价格权重
     + 速度适配分×速度权重
     + 菜系偏好修正
     - 明确拒绝惩罚
```

价格和速度不是“越低越无限加分”，而是衡量相对用户上限的余量。所有得分限制在 0–100。

### 5.4 三结果重排序

- 主推荐：综合得分最高。
- 时间更稳：在高分候选中提高速度因子的比重。
- 营养更优：在剩余高分候选中提高健康因子的比重。

结果必须去重。未来应增加商家、菜系和价格带多样化，避免三个结果形式不同但本质相同。

## 6. 解释生成

### 6.1 解释原则

1. 每份推荐同时说明一个主要理由和一个主要取舍。
2. 只能引用输入数据与计算因子，不生成菜单中不存在的食材或功效。
3. 不使用“绝对健康”“减脂必选”“适合糖尿病”等医疗化语言。
4. 营养值使用区间；低置信度必须可见。
5. 解释长度以 5 秒内读懂为目标。

### 6.2 生成约束

若未来使用语言模型，输入只提供选中菜品的结构化属性和允许引用的证据字段；输出使用固定 JSON Schema，并在展示前执行字段校验和敏感表述检测。

### 6.3 错误示例

| 不合格解释 | 问题 | 合格改写 |
|---|---|---|
| “这道菜富含维生素，能帮助减脂” | 菜单无依据且含功效承诺 | “蔬菜占比较高；热量为估算区间” |
| “绝对不会超预算” | 未考虑配送费或实时优惠 | “当前模拟总价在 32 元预算内” |
| “适合乳糖不耐受” | 过敏与配料信息不完整 | “未标记乳制品；不能替代过敏原核验” |

## 7. 数据置信度

| 等级 | 使用条件 | 展示方式 | 可否参与排序 |
|---|---|---|---|
| 高 | 商家明确标注份量与营养，或有稳定标准菜谱 | “高置信度”+区间 | 可以 |
| 中 | 菜名、主要食材和常见份量可推断 | “中置信度”+更宽区间 | 可以，降低健康权重影响 |
| 低 | 份量、配料或做法缺失 | “低置信度”+显著提示 | 可以，但不得作为营养更优首选 |
| 不可用 | 关键字段冲突或数据过期 | 不展示营养值 | 仅按其他因子排序或剔除 |

## 8. 安全与隐私边界

- 原型中的排除项是偏好过滤，不是过敏原保障。
- 真实产品收集敏感饮食信息前需单独说明用途、保存期限和撤回方式。
- 不从单次行为推断疾病、宗教、怀孕或身体状况。
- 推荐日志使用匿名用户 ID，不记录精确住址、支付信息和聊天原文。
- 商业推荐必须标记，且不得绕过硬约束或降低营养置信度标准。
- 发现数据过期、字段缺失或模型异常时，优先少推荐或不推荐。

## 9. 离线与在线评估

### 9.1 离线基准

| 评估项 | 数据集 | 指标 | 通过标准 |
|---|---|---|---:|
| 硬约束 | 150 道菜×边界条件组合 | 违规率 | 0 [T] |
| 营养区间 | 有人工/公开基准的菜品 | 高置信区间覆盖真实值比例 | ≥80% [T] |
| 排序相关性 | 用户对候选的成对选择 | NDCG@3 或 Top 3 命中 | ≥0.75 / ≥70% [T] |
| 解释忠实度 | 随机抽样解释 | 引用不存在字段的比例 | 0 [T] |
| 结果多样性 | 每次三选一 | 重复菜品率 | 0 [T] |

### 9.2 在线行为

- Top 3 至少一个被保留的会话占比。
- 首选直接选择率、替换率和解释展开后的选择变化。
- 60 秒有效决策率。
- 餐后准确度≤2 分的比例。
- 低置信度结果曝光率与被采用率。

## 10. 失败模式与降级

| 失败模式 | 用户风险 | 检测 | 降级策略 |
|---|---|---|---|
| 实时价格缺失 | 超预算 | 字段完整性检查 | 不展示该菜或标记需二次确认 |
| ETA 过期 | 迟到 | 时间戳与平台回传 | 重新查询；失败则移出“时间更稳” |
| 无候选 | 用户卡住 | 候选数为 0 | 明示哪条约束最限制结果，等待用户调整 |
| 营养低置信 | 误导健康判断 | 置信度规则 | 不进入“营养更优”，隐藏精确数字 |
| 解释生成失败 | 理由与数据不一致 | Schema 与证据字段校验 | 使用确定性模板解释 |
| 偏好学习漂移 | 越推越窄 | 多样性和拒绝监控 | 降低历史权重，允许一键重置偏好 |

## 11. Build / Buy / Wizard-of-Oz 决策

| 能力 | 验证阶段决策 | 理由 |
|---|---|---|
| 推荐排序 | 自建轻量规则 | 可解释、可测试，足够验证三选一价值 |
| 自然语言解析 | 先不构建 | 表单已能验证核心需求，避免引入解析风险 |
| 营养数据 | 人工标注小样本 | 先测试用户是否使用，再决定购买或估算 |
| 推荐解释 | 模板优先 | 避免幻觉，能验证信息结构 |
| 实时菜单与配送 | 寻找授权合作 | 不以抓取规避商业和合规风险 |
| 餐后个性化 | 本地轻量偏好 | 证明反馈闭环，不需要复杂模型 |

这个方案体现的 AI 产品原则是：先使用最小复杂度验证用户价值，把模型能力投入到规则难以处理、且能被评估的环节。
