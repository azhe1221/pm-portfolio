# 「审得快」用户研究与 JTBD

> 阶段：02｜用户研究与问题定义  
> 文档状态：研究计划与待验证画像  
> 真实用户样本：`N=0` [F]  
> 重要限制：本文不包含真实用户洞察、真实引语或已验证痛点

## 0. 研究诚信说明

当前无法接触真实财务/行政访谈对象，因此本阶段采用“两层证据”设计：

1. **现在可做 [F]**：用模拟费用制度、合成票据和任务脚本检查业务逻辑、原型可理解性与技术链路。
2. **未来必须补做 [H]**：通过真实访谈、情境观察和任务测试验证问题频率、现有流程、责任边界与试点意愿。

文中的角色、痛点、行为和 JTBD 都是 **[H] 待验证假设**。示例话术只用于访谈设计，不是用户原话。

## 1. 研究目标

### 1.1 核心研究问题

| 类别 | 需要回答的问题 | 对产品决策的影响 |
|---|---|---|
| 问题强度 | 审核员每周处理多少单？哪些步骤最耗时、最容易返工？ | 判断是否值得做及切入哪一步 |
| 当前行为 | 用户现在如何收集、核对、退回和留痕？ | 决定产品入口和替代成本 |
| 规则特征 | 制度是否明确、稳定、可被机器执行？例外有多频繁？ | 决定规则引擎和人工兜底范围 |
| 信任与责任 | 用户何时愿意相信系统，何时必须亲自核对？ | 决定证据、置信度和审批边界 |
| 使用与采购 | 谁使用、谁配置、谁决策、谁付费？ | 决定 ICP、GTM 与商业模型 |

### 1.2 暂不试图证明

- 不通过模拟材料推断真实效率提升。
- 不用学生或普通职员的意见代替专业审核员证据。
- 不把“觉得有用”当成试点意愿或支付意愿。
- 不在没有授权的情况下收集真实发票、银行、税号或身份数据。

## 2. 假设用户分层

### 2.1 首要画像：财务/行政审核员

| 维度 | 假设内容 [H] |
|---|---|
| 工作环境 | 20–200 人团队；工具可能是企业聊天、邮件、表格和财务软件组合 |
| 触发场景 | 月末集中报销、出差后批量提交、制度更新后首次审核 |
| 核心任务 | 核对材料完整性、关键字段和公司制度，处理例外并留痕 |
| 最大阻力 | 材料分散、字段重复读取、规则依赖记忆、退回原因反复编辑 |
| 成功标准 | 快速定位问题，不漏掉风险，不失去最终控制，后续可追溯 |
| 采用顾虑 | AI 误读、员工过度相信“通过”、责任归属、数据泄露、接入成本 |

### 2.2 次要画像：报销员工

| 维度 | 假设内容 [H] |
|---|---|
| 触发场景 | 完成差旅、招待、采购后整理票据并提交报销 |
| 核心任务 | 一次提交正确材料，尽快获得报销 |
| 最大阻力 | 不清楚制度、附件要求和被退回后的修改动作 |
| 成功标准 | 提交前就知道缺失项和不符合项，并得到明确修复建议 |
| 采用顾虑 | 上传材料的隐私、系统误报、额外录入步骤 |

### 2.3 决策画像：制度/业务负责人

| 维度 | 假设内容 [H] |
|---|---|
| 核心任务 | 让费用制度一致执行，并掌握高频异常和规则效果 |
| 成功标准 | 规则版本明确、每次结果可解释、责任边界清楚 |
| 采用顾虑 | 制度配置成本、例外覆盖不足、审计和合规风险、投资回报不清晰 |

## 3. JTBD 定义

### 3.1 审核员核心 Job Story

> **当** 我收到一组格式不一的报销材料并准备审核时，  
> **我想要** 先看到已结构化的关键字段、对应证据和制度异常，  
> **以便** 把精力放在例外判断上，同时保留最终决定和可追溯记录。 [H]

### 3.2 报销员工核心 Job Story

> **当** 我准备提交一笔报销但不确定材料和制度要求时，  
> **我想要** 在正式提交前知道缺什么、哪里不符合以及如何处理，  
> **以便** 尽量一次提交正确，减少退回和等待。 [H]

### 3.3 制度负责人核心 Job Story

> **当** 费用制度需要在不同人员和场景中执行时，  
> **我想要** 知道系统依据哪个版本、哪些规则和证据给出结果，  
> **以便** 保证执行一致，并在规则不适用时由人处理。 [H]

## 4. JTBD 六要素价值主张

| 要素 | 当前定义 |
|---|---|
| 1. 目标用户 | **[H]** 处理高频费用报销的中小团队财务/行政审核员 |
| 2. 动机/工作 | **[H]** 更快发现材料和制度异常，减少重复核对与往返沟通 |
| 3. 当前做法 | **[H]** 在聊天、邮件、表格、文件夹与财务系统间手工比对 |
| 4. 解决方案 | **[D]** AI 提取与解释 + 确定性规则预审 + 人工最终确认 |
| 5. 改变后 | **[H]** 审核员从逐项检查转向证据复核和例外处理；员工获得明确修改清单 |
| 6. 替代方案 | 人工检查、OCR、通用大模型、完整费控系统；具体替代关系待竞品研究 |

价值主张陈述：

> 对需要处理高频、格式不一报销材料的中小团队审核员，「审得快」是一个可解释的费用预审工作台。它把票据信息、制度规则、异常证据和人工决定放在同一条可追溯链路中；相比只做录入的 OCR 或直接给结论的通用 AI，它让机器承担重复整理，让规则负责制度判断，让人保留最终控制。 [D/H]

## 5. 需求假设清单

### 5.1 功能性工作

- **[H]** 快速确认金额、日期、商户、票号和费用类别。
- **[H]** 检查额度、时间范围、附件完整性和字段一致性。
- **[H]** 识别未知或需要人工解释的例外。
- **[H]** 生成可直接发送给员工的补充/修改清单。
- **[H]** 保存规则版本、证据、修正和最终决定。

### 5.2 情绪性工作

- **[H]** 在高峰期仍对审核质量有把握。
- **[H]** 不因系统黑箱输出而失去控制。
- **[H]** 减少重复催问和“为什么又被退回”的沟通压力。

### 5.3 社会性工作

- **[H]** 审核员希望向管理者证明制度执行一致且有记录。
- **[H]** 员工希望被清楚告知问题，而不是被模糊退回。

## 6. 假设用户旅程

| 阶段 | 审核员当前行为 [H] | 潜在痛点 [H] | 需要的证据 |
|---|---|---|---|
| 接收材料 | 从聊天、邮件或系统接收票据和说明 | 材料分散、命名不一致 | 观察真实入口与材料类型 |
| 整理字段 | 打开附件并手工读取/录入 | 重复、易错、注意力消耗 | 任务计时、错误类型 |
| 对照制度 | 查制度或凭经验判断 | 规则分散、版本不明 | 制度样本、实际解释方式 |
| 处理例外 | 联系员工补充或解释 | 原因描述重复、上下文丢失 | 退回记录、往返次数 |
| 做出决定 | 通过、退回或上报 | 担心漏审和责任 | 决策标准、复核机制 |
| 留痕复盘 | 保存表格、聊天或系统记录 | 证据链不完整 | 审计/管理需求 |

完整的采用旅程、触点、情绪、关键时刻与产品机会见 [`06-用户旅程-信息架构-核心任务流程.md`](./06-用户旅程-信息架构-核心任务流程.md)。该图仍为验证前假设，不替代真实研究。

## 7. 研究执行方案

### 7.1 第一步：无真实数据的可执行研究 [D]

使用以下合成材料：

- 3 个模拟公司费用制度版本。
- 30 组覆盖正常、超额、缺附件、字段冲突和未知情况的合成报销包。
- 角色任务脚本：审核员、员工、规则负责人各 2–3 个任务。
- 结果记录：任务完成、误解点、字段修正、规则异议、决定是否与证据一致。

该步骤只能验证**方案内部一致性和基础可用性**，不能证明真实用户价值。

### 7.2 第二步：未来真实访谈计划 [H]

| 项目 | 计划 |
|---|---|
| 样本 | 5–8 名真实财务/行政审核员；2–3 名制度负责人；员工仅作为补充视角 |
| 筛选条件 | 最近 3 个月实际处理过费用报销；能描述最近一次具体案例 |
| 方法 | 45 分钟半结构访谈 + 最近一次报销流程回溯；条件允许时做情境观察 |
| 重点 | 真实频率、最耗时步骤、例外比例、材料入口、责任边界、现有工具、采购方式 |
| 数据保护 | 不收真实票据；要求受访者遮盖身份、账户、税号和公司敏感信息 |
| 分析方法 | 按触发、行为、痛点、替代方案、结果和证据强度编码，不统计虚假精确比例 |

### 7.3 访谈问题

1. 请回忆最近一次处理报销，从收到材料开始发生了什么？
2. 哪一步最需要反复打开文件或查制度？请举最近的例子。
3. 什么情况会直接退回，什么情况必须找负责人判断？
4. 最近一次退回往返了几次？每次缺了什么信息？
5. 制度更新时，谁负责解释和通知？如何确认使用的是正确版本？
6. 哪些错误绝不能让系统自行判断？为什么？
7. 如果系统标出异常，你需要看到什么证据才愿意采用？
8. 现有工具最不可替代的部分是什么？切换工具的成本在哪里？
9. 谁会批准试点？他们最关心的风险和结果是什么？

避免使用“你会不会用 AI 审核”这类引导性问题；优先追问已经发生的行为。

## 8. 假设验证标准

| 假设 | 最小证据 | 继续条件 [T] | 失败后的调整 |
|---|---|---|---|
| 重复核对是高频问题 | 真实任务回溯与观察 | 多名审核员独立描述相同高频步骤，且有具体案例 | 转向更窄的材料整理或员工提交检查 |
| 预审能减少返工 | 对照任务或小范围试点 | 退回原因识别更完整，且不增加总任务时间 | 优化输入、减少提示，或放弃预审入口 |
| 用户需要证据而非结论 | 证据卡有/无对照任务 | 有证据组理解与纠错更好 | 简化证据呈现，而非增加解释文字 |
| 制度可规则化 | 制度条款编码工作坊 | 高频规则可稳定表达，例外可明确转人工 | 限缩至字段/材料完整性检查 |
| 团队愿意试点 | 决策者访谈和明确下一步 | 愿意提供匿名流程、安排测试或签署试点意向 | 重新评估 ICP、场景和价值强度 |

## 9. 本阶段结论

**[D] 保留三个角色，但首版优先围绕审核员设计。** 在没有真实用户资源时，先用合成材料验证任务链路，同时把真实访谈设为进入受控试点前的硬门槛。当前画像和 JTBD 是研究假设，不是研究结果。
