# 阶段 11｜Demo 演示脚本与可执行测试场景

> 产品：「审得快」AI 费用报销预审助手  
> Demo 入口：[prototype/index.html](../prototype/index.html)  
> 当前 Demo：中保真、浏览器本地状态、仅合成案例；不会读取或发送真实文件。

## 1. 演示目标

面试 Demo 不以“展示页面数量”为目标，而是验证四个产品行为：

1. 低置信字段必须进入人工确认，而不是自动成为事实。
2. 修改输入后，旧规则结果必须失效并要求重算。
3. `UNKNOWN` 与 `EXCEPTION` 要有不同的解释和行动路径。
4. 人工决定、材料版本和规则运行必须能在时间线回放。

## 2. 演示前准备

**测试角色**：财务/行政审核员（面试官观察产品，演示者代操作）。

**初始条件**：

- 直接双击 `prototype/index.html`，无需启动服务器。
- 顶部显示“仅合成数据”。
- 案例入口中存在 `BX-0010`、`BX-0007`、`BX-0011`、`BX-0012` 四个预置案例。
- Demo 使用模拟规则集 `policy_demo_travel v1.2`；不连接真实财务系统。
- 每条路径开始前点击“重置演示”，避免前一条路径的本地状态影响下一条。

## 3. 推荐 4 分钟演示路径

### 场景 D1｜低置信字段修正与结果失效

**测试目标**：验证人工修正能改变输入版本，旧规则结果不能继续作为当前结论。

**初始条件**：打开 Demo 首页并点击“重置演示”；案例 `BX-0007` 显示“字段待确认”。

**操作步骤与预期**：

1. 进入 `BX-0007`，说明金额候选为 `¥286.00`，标签为“低置信 · 阻断”。
2. 点击金额字段的“修正字段”，将值改为 `268`，原因选择“原文与候选不一致”。
3. 点击“保存并重算”或等价保存动作。
4. 指出页面出现“运行规则检查”入口，说明现在还没有使用新输入自动得出结论。
5. 点击“运行规则检查”，等待结果页面。
6. 返回“字段与证据”，修改商户为“示例商旅服务（已核对）”。
7. 指出“旧结果已过期/需要重新运行规则”提示。

**验收结果**：

- 286 → 268 的修正被记录，字段状态变为人工修正。
- 修改字段后，旧运行不能作为当前决定依据。
- 页面要求重新运行，而不是静默沿用旧结果。
- 时间线保留字段修正和旧运行事件。

**讲解句**：

> 这里的重点不是金额输入框，而是“事实版本变化会让结论失效”。这是 AI 产品里比模型回答更容易造成生产事故的状态问题。

### 场景 D2｜UNKNOWN 与 EXCEPTION 的不同处理

**测试目标**：验证证据不足和明确异常分别解释，不把两者合成一个风险分数。

**初始条件**：重置 Demo，进入 `BX-0011`，直接运行规则。

**操作步骤与预期**：

1. 点击 `excess_explanation` 对应的 UNKNOWN 项。
2. 展示“为什么无法判断”、缺少的材料和建议补充项。
3. 关闭详情，点击 `travel_limit` 对应的 EXCEPTION 项。
4. 展示实际值、模拟阈值、差值、规则 ID/版本和证据链接。
5. 在行动清单中加入“补充项目负责人确认记录”。
6. 点击“进入人工决定”。
7. 指出“预审通过”为禁用态；选择“退回修改”，填写理由并关联 `travel_limit`。
8. 提交决定，展示成功态和只读记录。

**验收结果**：

- UNKNOWN 显示“缺少证据/无法判断”，不被描述成已经违规。
- EXCEPTION 显示明确的规则触发事实和行动清单。
- 存在 UNKNOWN 或 EXCEPTION 时，首版不允许预审通过。
- 退回决定必须有理由和关联问题，并进入审计时间线。

**讲解句**：

> UNKNOWN 是“我还不知道”，EXCEPTION 是“在已知事实下触发了规则”。如果把两者混在一起，审核员无法知道下一步是补证据还是处理违规。

### 场景 D3｜补充材料、版本和时间线回放

**测试目标**：验证补充材料不覆盖旧事实，系统可以基于新版本重新运行。

**初始条件**：重置 Demo，进入 `BX-0012`，状态为“等待补充材料”。

**操作步骤与预期**：

1. 点击“模拟代上传材料”或“补充材料 v2”。
2. 观察案例版本从 v1 变为 v2，材料列表新增超额说明材料。
3. 运行规则检查，进入结果页。
4. 打开“审计时间线”。
5. 依次指出 v1、要求补充决定、材料 v2、新规则运行等事件。

**验收结果**：

- 新材料生成新版本，不修改旧材料内容。
- 新规则运行有新的运行 ID，并以 v2 输入为依据。
- 时间线能够解释“为什么重新审、基于哪一版材料”。

**讲解句**：

> 在财务流程里，补充材料不是简单覆盖文件，而是一次新的事实版本。版本化是为了让审核员和制度负责人能够回放当时的决定。

## 4. 可选 1 分钟正常路径

适合面试官只给很短时间时使用：

1. 重置 Demo，进入 `BX-0010`。
2. 点击“运行规则检查”。
3. 指出所有规则为 PASS，但页面仍提示“需要人工决定”。
4. 点击“提交人工决定” → 选择“预审通过” → 提交。
5. 展示“人工决定已记录”和时间线。

**关键话术**：

> “规则检查全部通过”不是“系统自动审批通过”。我要求审核员主动提交决定，是为了把建议、规则结果和责任记录分开。

## 5. 边界和失败场景

| 场景 | 操作 | 预期 | 面试解释 |
|---|---|---|---|
| 低置信字段未处理 | 直接尝试运行规则 | 运行入口被阻断或要求处理字段 | 不确定事实不能进入自动链路 |
| 修改字段后直接提交 | 不重新运行规则 | 决定入口不可基于过期结果提交 | 决定必须绑定最新运行 |
| UNKNOWN 选择预审通过 | 打开人工决定弹层 | 选项禁用 | 首版优先保护安全边界 |
| 文件处理失败 | 创建案例页选择“模拟失败状态” | 显示失败原因、替换/重试，不进入规则 | 失败必须可见且可恢复 |
| 规则结果展开 | 点击 PASS 项 | PASS 不提供异常详情抽屉或不允许错误操作 | 只对需要行动的结果提供额外复杂度 |
| 页面无法打开 | 双击入口无响应 | 检查是否被浏览器本地文件策略拦截；改用 Chrome 打开 | 作品集 Demo 是静态文件，不依赖服务端 |

## 6. 演示禁忌

- 不要说“这是实际 OCR 准确率”；当前案例是预置/合成数据。
- 不要上传真实发票、身份证、银行账户或公司制度。
- 不要把“规则检查通过”说成正式审批通过。
- 不要演示原型没有实现的员工端通知、ERP 接入、付款或发票验真。
- 不要为了展示自动化而绕过 UNKNOWN、EXCEPTION 或人工决定门槛。

## 7. 演示结束收束

> 这个 Demo 目前证明的是状态设计和责任边界能够被操作，而不是证明业务价值已经成立。下一步我会用真实审核员完成同一套任务，拿到手工基线、误解点和规则维护成本，再决定是否扩大到真实数据和系统集成。
