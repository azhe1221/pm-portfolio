# 「审得快」项目立项与产品策略假设

> 阶段：01｜项目立项与策略探索  
> 项目性质：个人 AI 产品经理作品集 / 验证前方案  
> 当前证据状态：尚未开展真实用户访谈，真实用户样本 `N=0`  
> 产品名称：「审得快」（工作名）

## 0. 证据标记

| 标记 | 含义 | 面试表达方式 |
|---|---|---|
| **[F] 已知事实** | 已经发生或可由当前项目文件直接验证 | 可以称为事实，并说明来源 |
| **[H] 待验证假设** | 基于业务推演形成，尚无真实用户证据 | 只能称为假设，不称为洞察或结果 |
| **[T] 验证目标** | 为后续实验预先设定的通过标准 | 只能称为目标值，不称为已达成指标 |
| **[D] 设计决策** | 当前方案的选择及其取舍 | 可以解释判断逻辑，不声称用户已认可 |

## 1. 一页式立项摘要

| 项目要素 | 当前定义 |
|---|---|
| 一句话定位 | **[D]** 面向中小团队的可解释 AI 费用报销预审助手，在人工审批前完成票据信息整理、规则核对与异常说明 |
| 首要用户 | **[H]** 20–200 人团队中兼任或专职处理费用报销的财务、行政人员 |
| 次要用户 | **[H]** 经常提交差旅、招待、交通等费用的员工 |
| 业务决策者 | **[H]** 费用制度负责人、财务负责人或公司管理者 |
| 核心问题 | **[H]** 审核人员需要重复核对票据字段、制度条款和附件完整性，并在材料有误时往返沟通 |
| 解决方案 | **[D]** AI 读取材料并结构化字段；确定性规则执行制度；系统给出证据与异常解释；人工做最终判断 |
| 核心验证目标 | **[T]** 在不削弱人工控制和可追溯性的前提下，提高“有效预审完成率”并减少重复核对 |
| 当前结果 | **[F]** 已完成产品策略、JTBD、流程、OST、风险优先级、MVP 与第 5 阶段 PRD/架构设计；尚无真实业务成效 |

## 2. 问题背景

### 2.1 初始问题陈述

**[H]** 在制度依赖人工解释、票据格式不统一、提交材料经常缺失的中小团队中，审核人员需要在多个文件和制度条款之间来回比对。大量时间可能消耗在“读、找、核、问”而不是需要专业判断的例外处理上。

初始问题拆为四类待验证现象：

1. **读**：从发票、行程单、支付截图中重复读取金额、日期、商户和票号。
2. **找**：定位费用类型对应的制度、额度和必需附件。
3. **核**：逐项检查字段一致性、额度、时间范围、重复报销与材料完整性。
4. **问**：发现问题后，重新组织原因并联系员工补充或修改。

这些现象目前均为业务假设，不能作为真实用户结论。

### 2.2 为什么选择这个题目

- **[D] AI 适配性**：票据理解和异常说明适合由模型辅助；制度合规适合由确定性规则保证。
- **[D] 产品判断空间**：核心不是做一个聊天机器人，而是设计 AI、规则和人工之间的责任边界。
- **[D] 原型可验证性**：可用合成票据和模拟制度完成端到端任务，不需要接触真实财务数据。
- **[H] 业务价值**：若重复检查频率高，减少返工可能同时改善审核效率和员工提交体验。
- **[H] 商业空间**：中小团队可能需要比完整费控系统更轻量的预审能力，但支付意愿尚未验证。

## 3. 产品愿景与定位

### 3.1 产品愿景

**[D]** 让财务人员从机械核对中释放出来，把时间用在真正需要判断、沟通和风险控制的事项上。

### 3.2 产品定位

「审得快」不是自主审批代理，而是一个**有证据、可追溯、由人兜底的报销预审工作台**。

```mermaid
flowchart LR
    A["原始报销材料"] --> B["AI：读取与整理"]
    B --> C["规则：执行公司制度"]
    C --> D["系统：解释异常与证据"]
    D --> E["人工：最终审核决定"]
```

### 3.3 差异化主张

| 常见替代方式 | 优势 | 主要缺口假设 | 「审得快」的目标差异 |
|---|---|---|---|
| 人工表格 + 文件夹 | 灵活、无需部署 | 重复核对多、难统一留痕 | 自动整理字段、规则结果和审计记录 |
| 通用 OCR | 快速录入字段 | 不理解公司制度，也不负责异常处置 | OCR/文档理解后继续执行制度检查 |
| 通用大模型 | 能阅读和解释 | 输出不稳定，决策依据难审计 | 结构化输出、规则判定、人类最终决策 |
| 完整费控系统 | 流程、支付、财务集成完整 | 对小团队可能过重、实施成本高 | 先聚焦提交前/审批前预审这一窄环节 |

以上差异均为 **[H]**，需在竞品研究和用户验证后修正。

## 4. 用户与角色

| 角色 | 待完成的核心工作 [H] | 产品价值假设 [H] | 权限边界 [D] |
|---|---|---|---|
| 财务/行政审核员 | 快速识别材料和制度异常，并保留判断依据 | 少做重复核对，更聚焦例外 | 查看、修正、预审、退回、要求补充 |
| 报销员工 | 提交前知道缺什么、错在哪里、如何修改 | 降低被退回和反复沟通 | 上传、补充、确认本人材料；不可修改规则 |
| 制度/业务负责人 | 确保规则被一致执行，问题可以追溯 | 看见规则执行情况与高频异常 | 配置/批准规则版本；不由 AI 代替审批责任 |

## 5. 首版能力地图

### 5.1 五项核心能力

1. **材料读取**：从合成发票和附件中提取金额、日期、商户、发票号码、费用类别等字段。
2. **证据对照**：每个字段显示来源位置和置信度，允许审核员修正。
3. **规则预审**：使用公司模拟制度检查额度、日期、附件、字段一致性等条件。
4. **异常解释**：明确显示“哪条规则、哪项证据、为什么异常、下一步做什么”。
5. **人工闭环**：由审核员确认通过、退回或要求补充，并保留完整审计记录。

### 5.2 产品责任边界

**首版做什么 [D]**

- 上传合成或匿名化报销材料。
- 结构化抽取字段并显示证据与置信度。
- 运行版本化模拟费用制度。
- 输出通过、异常、未知/需人工复核三种结果。
- 支持人工修正、确认与审计留痕。

**首版不做什么 [D]**

- 不自动付款，不自动作出最终审批。
- 不提供税务、法律或会计专业结论。
- 不承诺识别伪造票据或完成税务验真。
- 不建设完整费控、预算、总账或复杂审批系统。
- 不接入真实企业财务系统和真实个人财务数据。

## 6. 产品策略取舍

| 策略问题 | 当前选择 [D] | 选择理由 | 代价/风险 |
|---|---|---|---|
| 服务谁 | 先服务中小团队审核人员 | 工作流较短，便于验证窄场景 | 可能支付能力较弱 |
| 从哪里切入 | 审批前“预审” | 可创造价值，又不越过最终决策权 | 仍需嵌入现有流程才能产生真实价值 |
| AI 做什么 | 读取材料、归纳和解释 | 能处理非结构化信息 | 抽取错误需证据和人工纠正机制 |
| 规则做什么 | 公司制度的确定性判断 | 稳定、可测试、可审计 | 制度可能无法被完整规则化 |
| 人做什么 | 修正事实、处理未知、最终决定 | 保留责任和控制 | 无法做到真正全自动 |
| 如何验证 | 合成材料 + 模拟制度 + Wizard-of-Oz | 无真实数据也可先验证任务和交互 | 不能替代真实业务验证 |

## 7. 阶段目标与成功条件

### 7.1 当前项目目标

不是证明产品已经提升效率，而是形成一套可被验证的产品方案，并回答：

1. **[H] 价值**：重复预审是否足够高频、痛苦且值得解决？
2. **[H] 可用性**：审核员能否理解证据、置信度和三态结果？
3. **[H] 可行性**：文档字段能否稳定抽取，制度能否转成可执行规则？
4. **[H] 商业可行性**：团队是否愿意试点并为轻量预审付费？

### 7.2 阶段性成功标准

| 阶段 | 目标 | 退出条件 |
|---|---|---|
| 问题验证 | 证明重复核对和返工真实存在 | 真实访谈/观察形成稳定模式；当前尚未开展 |
| 概念验证 | 证明字段、规则、解释链路可理解 | 合成任务测试达到预设可用性目标 [T] |
| 技术探针 | 证明抽取和规则引擎达到最低可靠性 | 关键字段、规则和低置信降级达到目标 [T] |
| 受控试点 | 证明可嵌入真实工作流并产生价值 | 获得真实团队授权与合规评审后再定义 |

## 8. 立项结论

**[D] 继续进入问题与流程定义，但不直接建设自动审批系统。** 最关键的产品判断是把“AI 看懂材料”“规则执行制度”“人工承担决定”拆成三层，并优先验证制度规则化与用户价值两项生死假设。
